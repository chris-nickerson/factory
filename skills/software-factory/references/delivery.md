# Full delivery

You, the coordinating session, implement the change and own Git operations. Identify checks that apply to every viable design. Before you save a contract that selects a design, settle any requested consensus and [surface consequential choices](local.md#consequential-design-choices). Record the work branch and its base. Before implementing, start the evidence run against the base of the whole branch with review required. If the evidence shows the task needs no code change, record why and stop.

For a review-ready PR, freeze the coordinating task, including the requested endpoint. Give an implementation agent its own narrower brief when it must leave review or publication to you. When the user asks for design consensus, wait for the confirmed decision from `factory consensus design` before implementation. Record how reviewers will observe the changed behavior. For a UI change, include a check that drives the requested screen and user action. Record where the screenshot or recording must be posted.

Implement the agreed design and run the frozen checks. Checkpoint the scoped implementation on the work branch before handing it to the simplifier. Use the simplification command with the round count selected for this change, with the original base, scoped paths, acceptance checks and requested publication mode. Keep a record of both run IDs. An unavailable required role leaves full delivery pending. Reuse the same run ID when resuming that phase.

After the final scheduled checkpoint, run the independent review with `factory review` on the whole final change and replay the behavioral and engineering checks on the final subject. A changed head invalidates earlier review and check evidence. Adjudicate a finding using the actual trigger and source, repair confirmed blockers, then refresh review and final checks. Preserve the completed simplification count. Factory picks a reviewer from a different vendor than the last writer when one is available. Report any [reduced assurance](roles.md#reduced-assurance) with the result.

## PR review workflow

Use the target forge through the host's authenticated tools. Read applicable repository and user instructions, including any review skill the host exposes. Follow their rules for checks, evidence, reviewers, replies and queueing. Use the steps below wherever local instructions leave a gap. When opening a PR or updating its description, use the [PR writing guide](pr-descriptions.md). A fresh checkout with no review skill uses the same workflow.

1. Establish the requested endpoint, ordering and any round limit. Before opening or editing a PR, verify the repository, base and remote head against any prior receipts. On resume, carry forward the completed rounds. Reuse the matching PR or open it in the requested state when the user asked for a PR and none exists. When asked to mark it ready, promote the intended draft and verify the transition. Respect an explicit draft or ready-only stopping point.
2. Monitor current-head CI and requested reviews. Investigate a terminal failure as soon as the requested ordering permits, especially when it prevents reviewers from starting. Inspect job logs, review threads, PR comments and any applicable QA plan. Recheck the head before using a result. An approval on a different revision or a skipped check is evidence only for what it covered.
3. Triage each new finding against the code. Fix valid findings and in-scope CI failures together, run affected checks and recheck the remote head before pushing. Reconcile concurrent updates without overwriting them. Reply with the fix and its evidence, or the reason a finding does not apply. Resolve addressed threads according to local policy; leave genuine disputes open. Refresh the PR evidence after a change.
4. One round covers triage on one head and publication of any fixes. Repairing failed CI consumes that round even when the failure prevented reviewers from starting. At the round limit, read back the published head, checks, approval and unresolved threads once, then return. Wait for replacement CI only when separately requested. For continued babysitting, repeat on material changes. If only human approval remains, report whose action is needed. Use the host's wait mechanism between checks; respect any deadline and report a stalled check with its last observed state.
5. Stop at merge-ready by default. Merge only within the authorized endpoint, with the required approvals and checks on the intended head, using the repository's normal protections. If the forge cannot perform a required action, report the missing access or capability and the last verified state.

For full delivery, read back the simplification checkpoints and the final `factory status`. Confirm the requested rounds finished and the final checks and independent review passed on the final revision. When the task includes a PR, check on the forge that the PR reached the requested state and that reviewers can open the required evidence from it. For work on an existing PR, verify the checks and evidence required by that task. When UI evidence is required, inspect the recording or screenshots to confirm they show the requested screen and action. An image of a generated file proves what the renderer produced.

Monitor required jobs and send progress updates until the requested stopping point. At a round limit, use step 4. If a browser test stops before reaching the changed screen, investigate the failure and continue the other checks and repairs. If completing a required step needs new access or a person's action, say exactly what is blocked after completing the independent work. For a status question during delivery, answer it and continue to the requested endpoint.

At handoff, give the outcome, the revision reviewers saw, the observed runtime results and any published revision. State how many rounds finished and what still blocks the requested endpoint so the next session can resume.
