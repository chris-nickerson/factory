# Hill-climbing

Use this when the task calls for repeated changes to a measurable outcome. For a single comparison, use the [baseline guidance](local.md#choose-the-baseline).

1. **Define a win.** Name the outcome someone experiences, the population, the unit and direction of improvement. Set the smallest gain worth keeping, what must stay within bounds (such as correctness or cost per completed task), and the available trials, time or spend. Use the project's own runner. Freeze the metric, workload and guardrails in a [Factory contract](local.md). Reuse checked-in fixtures. Keep generated results and trial notes outside the checkout, and keep confirmation inputs and labels out of the tuning agent’s context.
2. **Check the measurement.** Run the current version on representative cases. Count failures and retries, and check what the denominator leaves out. Inspect examples the grader accepts and rejects against the actual outcome. Repeat noisy measurements in comparable conditions. If a label, grader or instrument is wrong, correct it and measure the baseline again under a new contract. A broken measurement cannot select a winner.
3. **Choose one change.** Use development cases and traces to find the largest loss you can affect. For latency, trace the path to the user-visible event. Shortening a long step that overlaps other work may save no waiting time. For agent behavior, inspect failed actions and final state. Predict which outcome will move and why. Keep confirmation cases or a later representative traffic window separate from the examples used to tune.
4. **Compare with the best supported version so far.** Change one plausible cause and replay matched work. Record the revision, prediction, result, guardrails and decision, including failed trials. Run `factory check RUN_ID` on each candidate while the contract is fixed. Carry forward a gain only when it exceeds ordinary variation and preserves the guardrails. Keep the previous best when evidence is inconclusive. Stop at the agreed target or budget, or when the remaining failures give you no credible next change.
5. **Confirm before claiming a win.** Check the selected candidate against the original baseline on untouched cases or independent field measurements. If fresh evidence fails to show a meaningful gain or a guardrail fails, keep the last independently supported version. If confirmation scores guide another edit or help rank further candidates, reserve fresh evidence for the final claim. Report the user-visible outcome, observed spread and limits. If only a lab proxy improved, record the field measurement still needed and attach it later with [`factory outcome`](local.md#later-outcomes).
