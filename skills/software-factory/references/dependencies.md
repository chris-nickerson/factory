# Dependency updates

Use the target repository's package manager, registry settings and checks. Follow the [local verification workflow](local.md) to verify the resolved version and the code that uses it. If a scanner reported the problem, also track its result on the updated revision.

- **Resolution.** The intended version resolves in every affected install root, across direct and transitive paths and relevant platform or optional variants.
- **Compatibility.** The code that uses the package still works with the resolved version.
- **Scanner disposition.** For an alert, the scanner's own result on the updated revision. Local evidence cannot settle this claim. A skipped scan or a scan on a sibling PR leaves it open.

1. **Identify the target.** For a routine update, establish the requested version or constraint and the compatibility the caller needs. For an alert, read the blocking finding on the scanned revision. Match the ecosystem, package, affected range and fixed release on the applicable version line against the advisory or maintainer notice when available. If sources disagree or no advisory exists yet, record what the scanner reports. Suspected malware, impersonation or unexpected install scripts call for supply-chain incident triage before installing anything. If no compatible fix exists, report the remaining options and their impact.
2. **Trace the resolution.** Check the work branch, intended base and any existing fix before regenerating locks. For an alert, also check which revision the scanner evaluated. If the base already contains the fix, verify that bringing the branch up to date clears it. Use the manifests, lockfiles and dependency graph to find direct and transitive parents and independently installed workspaces. One scanner occurrence count can cover several paths to the same package.
3. **Make the smallest compatible update.** Prefer a targeted resolution with the project's pinned manager. Change a direct constraint or upgrade a parent only when necessary. Treat an out-of-range override or major runtime migration as a separate compatibility decision. Review the resolved versions, sources, integrity data and incidental lockfile churn. Preserve the configured package source. A registry access failure leaves verification incomplete.
4. **Verify each claim.** At each affected install root, install from the lock using the project's frozen-install procedure. For a project without a lockfile, install from its declared requirements in a clean environment. Inspect the resolved graph and check the installed versions against the target. A lockfile consistency check alone leaves installation unverified. Run the same consumer check on the baseline and the candidate. For an alert, obtain the scanner's result on the updated revision.

Report the old and new resolutions, the install roots and consumers checked, the scanner disposition when applicable, and any remaining exceptions. Use the repository's delivery process for the requested endpoint.
